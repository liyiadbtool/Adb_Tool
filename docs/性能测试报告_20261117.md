# 性能测试报告 · 2026-11-17（基线 A26）

> 背景：现场反馈 `adb_Tool.exe` CPU 99.7%，风扇拉满。
> 本机（Ultra 5 225H / 12 逻辑核）**空闲时实测 0%**，复现不出，所以改成
> "把每个可测环节量化 + 找出结构性问题、改掉、再量化"。

---

## 1. 方法（先说口径，避免假数据）

| 环节 | 怎么测 | 注意 |
|---|---|---|
| DOM 渲染 | `377/_bench_render.py`：Edge headless **真实时钟**，`DOMContentLoaded` 里同步跑完写 `<pre>` | **不能用 `--virtual-time-budget`**：虚拟时钟下 `performance.now()` 不前进，新旧写法都返回 `0.0ms`（我第一版就踩了这个坑） |
| 启动耗时 | 包一层计时 `adb_Tool.exe --exec ":h"`（`:h` 本身瞬时，差值即启动开销） | 本机当前负载很重（用户同时跑 CAN 采集/回放），绝对值偏悲观 |
| 空闲资源 | `Get-Process` 取 `CPU` 增量 + `WorkingSet64`，采样 4s | `CPU` 是累计 CPU 秒，用两次差 |
| 门禁 | `python verify_all.py` | 28 项，含 12 套 headless |

---

## 2. 结果

### 2.1 DOM 渲染（logcat 满速时的主战场）

`appendLines` 一批 500 / 2000 行，且**日志区已在 5000 行上限**（logcat 持续刷就是这个稳态）：

| 场景 | 改前（逐行 append + 每行 trimLog） | 改后（Fragment 一次插入 + 一次裁剪） | 提升 |
|---|---|---|---|
| 500 行 · 上限态 | **34.8 ms** | **13.3 ms** | **2.6×** |
| 2000 行 · 上限态 | **136.9 ms** | **53.5 ms** | **2.6×** |
| 500 行 · 空箱 | 1.0 ms | 0.6 ms | 1.7× |

**这张表解释了 99.7%**：泵血节拍是 **33 ms**（`GuiWeb.PumpOutput` 有积压时），
而旧路径处理一批 500 行要 **34.8 ms —— 比节拍还长**。
只要 logcat 持续输出，UI 线程每一拍都做不完，队列永远积压 →
CPU 长时间贴着单核 100%，风扇自然拉满。
改后 13.3 ms，节拍内有 60% 余量，才能"持续跑而不饱和"。

### 2.2 启动

| 项 | 实测 | 说明 |
|---|---|---|
| `--exec ":h"` 总耗时 | **3391 / 2961 / 3074 ms** | 三次。`:h` 本身是本地输出，所以这 3 秒全是启动开销（进程启动 + .NET 装载 + ini/cmds/历史 + `Bg.Start`）。**未逐项归因**，不写"已优化" |
| 参照：单次 `adb version` | 1104 / 1238 ms | 本机负载下 adb 调用本身就要 1.2s，任何"启动时探一次设备"的路径都会付这个钱 |

### 2.3 空闲与门禁

| 项 | 实测 |
|---|---|
| 空闲 CPU | **0.00 s / 4 s（≈0%）**，两个进程（6 MB 宿主 + 64 MB 主进程） |
| 空闲内存 | 64 MB 工作集 |
| 全量门禁 | **1 分 34 秒**（28 项，12 套 headless + 起一次真窗） |

## 3. 已做的优化

| # | 改动 | 依据 |
|---|---|---|
| 1 | `appendLines` 按槽位分组 → 一次 `DocumentFragment` 插入 → 一次 `trimLog` → 一次贴底 | 2.1 表：34.8 → 13.3 ms。原来是 500 次布局失效 + 500 次裁剪扫描，现在是各 1 次 |
| 2 | `trimLog` 把提示节点缓存到 `box.__trimNote`（A24 已做） | 满量后每行的 `querySelector` 全子树扫描消失 |
| 3 | `377/_test_interaction.py` 加批量渲染回归（行数/顺序/多槽分流） | 防止以后有人"顺手"改回逐行 |

## 4. 还没做、但值得做的（按收益排序）

| # | 候选项 | 预估收益 | 风险 |

| 2 | **启动 3 秒归因** | 中。若大头是同步 adb 调用，改成"窗口先出、设备后探"可省 1~2s | 中（`App.ADB` 被多处读，要防竞态） |
| 3 | **裁剪从"逐条 removeChild"改为 Range 批量删** | 低-中。剩余 13.3ms 里裁剪占大头（未单独量化完） | 低 |
| 4 | **`MAX_LOG_LINES` 5000 → 3000** | 低-中。节点越少，裁剪/样式重算越快 | 低（牺牲回溯行数） |
