# AI 协作指南：提示语模板 + 实现步骤

> 本文是这个项目（网联服务_Adb_Tool）从 0 到交付过程中，**真正跑通过**的提示语写法与工程步骤。
> 目的：下次提需求时照着写，AI 一次做对的概率高很多；接手新功能时照着做，不会漏测试和交付物。

---

## 一、提示语（按场景给模板）

### 1.1 新功能 / 新模块

结构：**目标一句话 + 交互细节 + 例外与边界 + 验收标准**

```
【目标】快捷指令页新增「APK管理」分组：下拉选应用，三个按钮（清空数据/关闭进程/导出APK），
        再加「查询全部版本」。
【交互】下拉只显示名称（用户自己起的，中文/英文都行），包名不显示但要能用来过滤；
        没选应用时三个按钮禁用；执行中禁用。
【存储】列表要持久化，关掉程序下次还在；名称和包名都不能重复。
【边界】包名会拼进 shell，必须白名单校验，不能出现注入；
        多 split 的包导出时必须全部拉下来，只导 base 装不上。
【验收】给出 selftest 断言数量 + UI 测试套件，并出两个交付包。
```

要点：
- **说清"例外"比说清"正常流程"更重要**。上面 4 条边界，每条都对应一个真实坑。
- 写"验收"，AI 就会主动把断言加进自检体系，而不是口头说"已完成"。

### 1.2 改交互（最容易来回改的一类）

结构：**现状 + 期望 + 明确的反例**

```
【现状】输出框有输出时会自动展开。
【期望】默认收起；用户输入指令也不打开；只有用户主动点才开。
【反例】不要"有输出就自动展开"，也不要"失败时破例展开"。
【补充】表头右侧加一个「收起」按钮，和 仅失败/复制全部/清空 一排。
【补充】折叠栏要显示"12 条 · 最近 失败 19:41"。
```

要点：
- 不给反例，AI 很容易保留"贴心"的自动行为（比如失败自动展开），下一轮你还得再提一次。
- 改动会牵连测试与文档，明确要求「同步改断言和手册」，否则会出现代码对了、文档还写着旧行为。

### 1.3 修 bug（要求找根因）

结构：**现象 + 复现 + 已知条件 + 禁止绕**

```
【现象】设备连上后没有自动重连；界面一直停在未连接，重启程序才好。
【复现】程序运行中执行 adb kill-server，再 start-server，设备回来了但界面没反应。
【已知】不是没检测到设备（adb devices 里有）。
【要求】找根因，不要用"定时轮询重试"绕过去；修完要在真机上验证并给日志时间线。
```

要点：
- "不要用轮询绕过去"这句很关键，否则容易得到一个能跑但很脏的方案。
- 要求"给日志时间线"，AI 就必须真的跑一遍，而不是只改代码。

### 1.4 口径类（文案/判定，最容易埋雷）

```
【要求】pm clear 的按钮叫「清空数据」，不能叫「清缓存」。
【原因】它清的是全部数据（登录态、授权都没），叫缓存会误导用户。
【要求】判定必须有正向证据 Success，并且排除 Failed/denied/unknown package，
        因为 pm clear 失败时退出码仍是 0。
```

要点：**给原因，AI 才会把这条规则写进注释和自检**，而不是当一次性文案改掉。

### 1.5 回退（上一版做错了）

```
【问题】指令输入页敲完回车会跳到快捷指令页，实际用下来是反效果：连续敲命令会被弹走。
【要求】回退成"在哪个页面敲，输出就留在哪个页面"。
【要求】同步回退 _test_src_route.py 的断言和手册第 4 章，别留下与实现相反的测试。
```

要点：明确"这是回退"，并点名要同步的测试/文档；否则 AI 可能只改代码，留下红测试。

### 1.6 交付类（每次收尾都要）

```
【要求】每次生成完成准备两个交付产物：一个本地可运行包，一个已压缩好可直接分享的包。
【要求】交付前跑完全量回归并在报告里给出数字（CLI selftest / GUI selfcheck / UI 套件）。
```

要点：把"两个产物 + 回归数字"写进长期约定（本项目落在 `.workbuddy/memory/MEMORY.md`），
后续每次会话都会自动执行。

## 二、实现步骤（可复用的七步）

### Step 0　需求澄清（15 分钟省一天）

先问清六件事，答不上就先写"假设"再开工：

1. 改哪个界面/哪个命令？
2. 数据要不要持久化？存哪（`%LOCALAPPDATA%` 还是 exe 同级）？
3. 失败/为空/无权限时怎么表现？
4. 与现有功能有没有重叠（会不会出现两个入口做同一件事）？
5. 要不要动 CLI（命令行版）还是只动 GUI？
6. 验收怎么判定（数字、截图、还是真机日志）？

### Step 1　先读代码，别猜

- 用 `Grep` 找现有实现（`ls` 怎么渲染、`pull` 怎么调用、消息怎么路由）。
- 确认三件事：**现有协议字段**、**输出源约定（src=0/1/2/3）**、**谁在抢 `_busy`**。
- 典型收获：这次发现 `ls` 只取文件名（没有权限/时间/大小），所以文件管理器必须新写 `stat` 解析，
  而不是"复用一下 ls 就行"。

### Step 2　定协议（先定接口，再写实现）

前端 → 后端：`{kind, ...}`；后端 → 前端：`{kind, ...}`。写清楚四件事：

| 项 | 例子 |
|---|---|
| 请求 | `apkact {pkg, act}` |
| 响应 | `apkver {ms, rows[]}` / `apkack {ok, op, msg}` |
| 输出路由 | 动作输出走 `src=3`（面板），不污染反馈区 |
| 并发 | 复用 `_busy[0]`，忙时回 `end{busy:true}` |

> 这一步偷懒，后面一定会出现"输出跑到别的页面去了""按钮点了没反应"。

### Step 3　分层实现（数据 → 动作 → 协议 → UI）

以 APK 管理为例，四层各自独立、各自可测：

1. `ApkList.cs`：持久化 + 校验 + 迁移（纯逻辑，可自检）
2. `ApkCmds.cs`：按包动作（清数据/杀进程/导 APK），判定口径统一
3. `GuiWeb.cs`：消息处理 + worker + 推送
4. `ui.html`：面板、下拉、结果渲染

每层写完立刻编译，不要四层写完再一起编。

### Step 4　把断言塞进已有体系（不是新造一套）

本项目有三层测试，新功能往对应层里加：

| 层 | 入口 | 适合验什么 |
|---|---|---|
| 纯逻辑 | `adb_log_export.exe -selftest` | 解析、校验、判定、状态机 |
| GUI 内部 | `adb_Tool.exe --selfcheck` | 窗体/WebView 初始化、消息通道 |
| DOM 行为 | `377\_test_*.py`（headless Edge） | 交互、样式、路由、禁用态 |

经验：**纯函数优先**。写不动的逻辑（比如"重连该不该触发"）先抽成
`Decide(prev, now, curDev)` 这样的纯函数，再测 —— 否则永远只能靠真机碰运气。

### Step 5　回归（四件事都要做）

1. 编译两版（CLI + GUI），static check（`node _check_ui.js`）
2. 跑全部 DOM 套件（本项目 8 个文件）
3. **真机/真实启动**：GUI 起来跑 9 秒，看 `gui_trace.log` 有没有异常
4. 关键路径手测：这次用 `adb tcpip 5555` 制造瞬断，验证自动重连 + root 复核

> 真机这一步不能省。这次"重连不上"的根因（`ReadExact` 把断线当超时死循环）
> 就是靠 `adb kill-server` 复现 + trace 时间线定位的，纯看代码很难发现。

### Step 6　同步文档与记忆

- 行为变了 → 改 `docs\用户使用手册.md`（**同一轮就改**，别攒着）
- 关键取舍 → 写进 `.workbuddy\memory\MEMORY.md`（"别顺手优化回去"清单）
- 当天的改动 → 追加到 `.workbuddy\memory\<日期>.md`

### Step 7　出交付物（一条命令）

```bash
python release.py            # 编译 + 完整包 + 最小包 + 两个 zip
python release.py --no-build # 只重打包（改完页面快速出包）
```

产出：`dist\`（本地完整）、`dist_min\`（最小）、`release\*.zip`（分享）。

## 三、这个项目沉淀的硬规则（新会话必读）

| 规则 | 原因 |
|---|---|
| C# 5.0：不用 `$"..."` / `?.` / `out var` / 表达式体成员 | 系统自带 csc 是 .NET 4.x |
| 新增 `.cs` 必须同时加进 `_cs\build.bat` 和 `build_gui.bat` | 两个 bat 都是显式文件列表，不加就编不进去 |
| `.bat` 只写 ASCII 注释和路径 | cmd 按 GBK 读，UTF-8 中文会被拆成命令片段 |
| 可写数据一律进 `%LOCALAPPDATA%\adb_Tool\` | exe 可能放在无写权限目录 |
| 包名拼进 shell 前必须白名单校验 | `pm clear <pkg>` 是拼接执行 |
| 判定要有正向证据（`pm clear` 看 Success） | 失败时退出码仍可能是 0 |
| 后台能力必须写 trace（`watcher:`） | 无法在界面上复现的问题只能靠日志 |

## 五、给 AI 的"一句话开场"

如果懒得写长模板，至少给这三句：

```
1) 改哪个文件/页面，现状是什么。
2) 期望行为和明确的反例（不要什么）。
3) 验收标准（断言数量 / 真机验证 / 交付物）。
```

这三句齐了，基本不会跑偏；缺哪句，就会在那一项上返工。
