## 背景：为什么只吸收机制、不吸收功能

ClusterDebugTool 的**功能**强绑定仪表协议栈（PPS/SPI、LXC 容器、xlsx 协议表、
DID 参数组），我们没有那套协议，硬搬过来无法验证。

但它的**工程机制**是通用的、且经过真车验证的经验，值得吸收。

以下 4 项按优先级排列。

---

## R1 · 持久 shell 通道（优先级：高）

### 现状问题

我们每条命令都是一次独立的 `adb shell`：

```
adb shell xxx   ← 进程启动 ~100~300ms
adb shell yyy   ← 又启动一次
```

**成本被放大的场景**：

| 场景 | 每轮 shell 次数 | 影响 |
|---|---|---|
| 定时监听异常（mode 2） | 3 次 `ls` + 2 次 root/pidof | 每 30 分钟多花约 1 秒 |
| 诊断页每次刷新 | 1 次 `getprop`（含 5 个属性） | 可接受 |
| HeapDump 进程列表 | 1 次 `ps -A` | 可接受 |
| 将来若做「实时监控」 | 每秒多次 | **不可接受** |

### 对方怎么做

> 「通道建立后需要执行的初始化命令」
> 「初始化命令执行完后确认通道确实可用」
> 「后续所有仪表命令均在该存活通道内执行」
> 「应用退出时停止工作线程并关闭通道」

### 建议方案

```
启动时（或首次需要时）建立一个常驻 `adb shell` 子进程
  ├─ stdin  写入命令
  ├─ stdout 读取输出（按标记分帧）
  └─ 后台线程保活 + 断线重连
```

**风险与缓解**：

| 风险 | 缓解 |
|---|---|
| 通道卡死（命令挂住） | 每条命令设超时，超时就杀通道重建 |
| 输出粘连 | 用唯一结束标记分帧（见 R2） |
| adb 重连后通道失效 | 监听 adb devices 变化，掉线自动重建 |
| 并发访问 | 加锁 + 队列，避免两个线程同时写 stdin |

### 优先级理由

它不改变现有行为（可以做成"后台可选通道"，失败自动降级到现在的独立 shell），
但为将来做实时监控打开空间。**属于基础设施投资，风险低、收益中。**

---

## R2 · 提示符判据 + 唯一结束标记（双判据）

### 现状问题

我们判断命令结束靠 `ShellCall` 的超时（`CALL_TIMEOUT_MS = 30000`）：

- 命令无输出 → 干等 30 秒才返回
- 命令输出很慢 → 可能被超时误杀
- 命令有输出但没换行 → 无法判断结束

### 对方怎么做（比 R1 更细，是配套机制）

> 「等待标记整行出现即认为命令结束」
> 「避免匹配到命令回显里的同名文本」
> 「生成不会与设备输出冲突的唯一结束标记」
> 「即使提示符判断提前命中也不会丢命令」

**核心洞察**：单靠提示符会误判（命令输出里可能含提示符文本），
所以要**两个判据都要满足**：提示符出现 **且** 唯一标记出现。

### 建议方案

```bash
# 每条命令这样发：
echo __CMD_START_<随机串>
<实际命令>
echo __CMD_END_<随机串>
```

读取时以 `__CMD_END_<随机串>` 为界分帧，随机串保证不会和设备输出撞。

### 优先级理由

这是 R1 的**前置依赖**（没有分帧机制，持久通道无法可靠工作）。
但**即使不实施 R1，也可以先用在现有的单次 shell 上**——
能解决"无输出命令干等 30 秒"这个高频痛点。

---

## R3 · 路径自动纠正 + 回写配置（优先级：中）

### 现状问题

我们的 `config` 里路径是写死的（如 `platform-tools\adb.exe`、日志目录等）。
换机器、换平台、移动到别的目录后，配置指向不存在的路径，**静默失效**。

真实痛点：
- 用户把 dist 目录换个位置 → 内置 adb 找不到
- 不同平台路径不同 → 需要人工改配置

### 对方怎么做

> 「配置路径在仪表上不存在时自动纠正」
> 「本次开机内禁止再被任何方式拉起」
> 「解析出的绝对路径写回当前芯片配置文件」
> 「下次启动先检查配置里记录的路径是否还存在」
> 「最终仍缺失的项通过返回值告知调用方」

**设计要点**（这条最值得学）：
1. 启动时先检查配置里的路径是否存在
2. 不存在 → 按优先级重新解析（随包目录 → 系统 PATH → 内置）
3. 解析成功 → **写回配置文件**（下次直接命中）
4. 全部失败 → 明确告知调用方，不静默

### 建议方案

给 `config` 加一层 `ResolvePath(key)`：

```
ResolvePath("adb"):
  1. 读配置里的路径 → 存在？用它
  2. 不存在 → 尝试 随包 platform-tools\adb.exe
  3. 仍不存在 → 尝试 系统 PATH
  4. 仍不存在 → 尝试 内置 adb
  5. 成功则写回配置；失败返回空 + 记录日志
```

### 优先级理由

改动局部（只影响路径解析），但能消除一类"换机器就不好使"的隐性故障。
**建议在下次改动 adb 路径相关逻辑时顺带做掉。**

## R4 · 芯片 / 机型自动识别（优先级：中低）

### 现状问题

我们靠**人工选平台**（Max-8838-T75 / A8R_8295 / T09M_8295 / AHT / V20）。
选错了，指令就发到错误的平台，可能误操作。

### 对方怎么做

> 「读取设备属性自动识别芯片」
> 「用户无需手动选择芯片型号」
> 「未登录时自动识别芯片型号」
> 「插入设备时自动识别芯片并切换配置」
> 「切换后自动加载对应配置文件与机型逻辑」
> 「芯片切换后重建与配置强相关的界面内容」

### 建议方案

```
连接设备后：
  读 ro.product.model / ro.board.platform / ro.build.characteristics
  → 匹配机型表 → 自动选中平台
  → 若匹配不到，保留人工选择（不强猜）
```

**注意**：对方是"自动识别 + 无需人工"，我建议**自动识别 + 人工可覆盖**，
因为我们的车型多，误判后果比对方严重（对方是只读为主，我们有很多写操作）。

### 优先级理由

需要先建立可靠的「属性 → 平台」映射表（要真车验证每个平台的特征属性），
**成本不在代码，在数据收集**。建议等有了明确的属性对照表再做。

## 附：明确不吸收的项

| 项 | 原因 |
|---|---|
| PPS / SPI 协议下发 | 依赖 `/tmp/pps/spi_service_2/` 与 LXC，我们无此协议栈 |
| xlsx 协议表解析（指示灯/图文/声音报警） | 仪表专属 |
| DID 参数组读写（28 组 × 2 体系） | 仪表专属 |
| 协议回放（`config/auto_test/*.xml`） | 依赖信号级协议定义 |
| 登录 + 远程服务端 + 心跳 | 我们是纯本地工具，不应引入账号体系 |
| 54.5MB 的独立解码进程 | 我们直接调 scrcpy，不需要自带 ffmpeg |

## 实施建议顺序

```
第 1 步  R2（唯一结束标记）      ← 独立可做，立即收益：不再干等 30 秒
第 2 步  R3（路径自动纠正）      ← 独立可做，消除隐性故障
第 3 步  R1（持久通道）          ← 依赖 R2，收益较大
第 4 步  R4（芯片自动识别）      ← 依赖数据收集，最后做
```

每步都可以独立交付、独立回滚。
