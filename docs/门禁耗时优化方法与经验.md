> **这份文档给"下一个接手的人/设备/AI"看。**
> 讲清三件事：① 门禁时间到底花在哪 ② 怎么自己查出瓶颈 ③ 哪些优化试过、结论是什么。

## 一、结论先行

| 档位 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| `--fast` | 7s | **6s** | 已接近下限（全是静态检查） |
| 常规（无参数） | 85~241s（抖动） | **68s（稳定）** | 消除抖动，连测 3 轮 68/68/68 |
| `--full` | 305s | **168s** | 快 45% |

**最大收益不是"变快"，而是"变稳"。**
原来跑门禁像抽奖——同一份代码可能 85 秒也可能 241 秒，无法判断是不是自己改坏了。
现在 68 秒就是 68 秒，可以放心每轮都跑。

## 二、时间到底花在哪（逐套实测数据）

这是所有优化的依据。**不要凭感觉估，一定要逐套计时。**

### 2.1 测试逻辑本身很快

13 套浏览器测试，**逻辑执行合计仅 62.6 秒**：

| 套件 | 耗时 | 套件 | 耗时 |
|---|---|---|---|
| `_test_structure` | 4.3s | `_test_wadb_ui` | 2.9s |
| `_test_ui_behavior` | 3.5s | `_test_file_ui` | 5.2s |
| `_test_src_route` | 4.2s | `_test_fs_search` | 4.2s |
| `_test_busy_lock` | 3.7s | `_test_interaction` | 5.2s |
| `_test_batch_ui` | 4.4s | `_test_a32_motion` | 5.5s |
| `_test_apk_ui` | 3.0s | `_test_ui_compare` | 11.0s |
| `_test_settings_panel` | 5.5s | | |

### 2.2 但优化前它们分别要多久

| 套件 | 优化前 | 优化后 | 根因 |
|---|---|---|---|
| `_test_interaction` | **49s** | 5.2s | 优先真实 WebView2，每跑新建 profile 冷启动 |
| `_test_ui_behavior` | **10~50s（抖动）** | 3.5s | 同上 |
| `_check_v12` | **126s** | 5.5s | 缺启动参数 + 超时 120s 干等 ×2 |

**关键洞察：慢的不是"跑测试"，是"等浏览器启动"和"等超时"。**

### 2.3 非测试环节

| 项 | 耗时 | 说明 |
|---|---|---|
| 编译列表 / 功能清单 / 静态自检 | 0.2~0.4s 各 | 已到下限 |
| 功能不变量 | 1.3s | 44 项，含正则扫描 |
| CLI 自检 | 2.1s | C# 489 条断言 |
| `_test_profile` | **63s** | 起 12 次 exe，各 5.8s（WebView2 初始化），**压不动** |
| `_test_ux` | 9.7s | 逐像素比对，合理 |

`_test_profile` 的 63 秒是硬成本：每次 `adb_Tool.exe --exec` 都要初始化 WebView2 运行时，
无法通过参数绕过。**但它只在 `--full` 跑，不影响日常。**

## 三、怎么自己查出瓶颈（可复用的排查流程）

下次觉得"门禁变慢了"，按这个顺序查，不要瞎猜。

### 步骤 1：逐套计时，揪出最慢的 1~2 套

```python
import subprocess, sys, time, os
tests = ['_test_structure','_test_ui_behavior','_test_src_route','_test_busy_lock',
         '_test_batch_ui','_test_apk_ui','_test_wadb_ui','_test_file_ui','_test_fs_search',
         '_test_interaction','_test_a32_motion','_test_ui_compare','_test_settings_panel']
cwd = os.path.join(os.getcwd(), '377')
tot = 0
for t in tests:
    s = time.time()
    subprocess.run([sys.executable, t+'.py'], cwd=cwd, capture_output=True, timeout=200)
    d = time.time()-s; tot += d
    flag = '  <-- 慢' if d > 15 else ''
    print('%-24s %6.1fs%s' % (t, d, flag))
print('\n合计 %.1fs' % tot)
```

> ⚠ Windows Git Bash 里 `bc` 不可用，**用 Python 计时**，别用 shell 算术。

### 步骤 2：判断是"在等超时"还是"真在算"

**看实际耗时是否接近代码里的 `timeout` 值。**

```bash
grep -n "timeout=" 377/_test_xxx.py
```

- 实际 126s、`timeout=120` → **就是在干等超时**，不是真在工作
- 实际 5s、`timeout=120` → 正常，超时值是保险不是常态

### 步骤 3：同一条跑 3 次，看抖动

```bash
for i in 1 2 3; do
  S=$(date +%s%3N); python 377/_test_x.py > /dev/null 2>&1; E=$(date +%s%3N)
  echo "第${i}次: $((E-S))ms"
done
```

- 3 次接近（如 4.2 / 4.5 / 4.3）→ 稳定
- 差 3 倍以上（如 12 / 27 / 19）→ **抖动**，通常是固定等待撞上环境抖动

### 步骤 4：检查启动参数是否统一

这一步最容易漏。查哪些套件缺优化参数：

```bash
for f in 377/_test_*.py; do
  H=$(grep -c "no-first-run" "$f")
  echo "$(basename $f): $H"
done
```

出 0 的就是缺参数。**这类"某个文件有、别的文件没有"的差异，是耗时优化的金矿。**

### 步骤 5：确认没有重复等待

有的套件存在"页内自适应等待 + 外层固定等待"两层叠加。
页内 `waitSteady()` 已经在轮询到稳态就继续，外层再死等 3.5 秒就是纯浪费。

## 四、实际做的 5 项优化

### 优化 1：默认改走 headless Edge（收益最大）

**改了什么**：`_test_interaction`、`_test_ui_behavior` 默认通道从真实 WebView2 改为 headless Edge。

**怎么验证没有降低检出能力**（这一步必须做，不能凭感觉）：

```bash
# 两条通道各跑一次，对比断言清单
UI_CHANNEL=wv2     python 377/_test_ui_behavior.py > /tmp/wv2.txt 2>&1
UI_CHANNEL=headless python 377/_test_ui_behavior.py > /tmp/hl.txt 2>&1

# 归一化 HTML 转义后逐行对比
diff <(grep "^  PASS\|^  FAIL" /tmp/wv2.txt | sed 's/&gt;/>/g;s/&lt;/</g') \
     <(grep "^  PASS\|^  FAIL" /tmp/hl.txt | sed 's/&gt;/>/g;s/&lt;/</g')
```

**实测结果**：

| 套件 | WebView2 | headless | 断言对比 |
|---|---|---|---|
| `_test_ui_behavior` | 50s / 277 条 | 4.5s / 277 条 | **逐条一致** |
| `_test_interaction` | 49s / 34 条 | 6.2s / 34 条 | **逐条一致** |

差异只有 `>` 与 `&gt;` 的 HTML 转义，**断言内容完全相同**。

**兜底**：`UI_CHANNEL=wv2` 可切回真实 WebView2，需要"线上同款渲染器"时用。

> 历史注释曾担心"headless 虚拟时钟冻结 transition，等不到稳态"。
> 实测未出现，同时把 `--virtual-time-budget` 从 9000 提到 12000 作为保险。

### 优化 2：统一补 Edge 启动优化参数

6 个参数，减少冷启动时的后台活动：

```python
EXTRA = ['--no-first-run', '--no-default-browser-check',
         '--disable-background-networking', '--disable-sync',
         '--disable-extensions', '--disable-component-update']
```

**改动前**：只有 `_test_interaction` 有，其余 16 套全缺。
**效果**：单套省 1~3 秒。

### 优化 3：超时值合理化

| 文件 | 原值 | 新值 | 理由 |
|---|---|---|---|
| `_wv2.py`（dump / dump_dom） | 180s | 45s | 卡住快速失败，不干等 3 分钟 |
| `_check_v12.py` | 120s | 45s | 卡住换 profile 重试（共 3 次），而不是等 2 分钟 ×2 |
| `verify_all.py` 单套超时 | 240s | 120s | 实际最长 11s，240 秒纯属浪费 |

> 原则：**超时值是"保险"，不是"预期耗时"**。
> 设成实际耗时的 3~10 倍即可，设成 20 倍就是在惩罚自己。

### 优化 4：去掉套件间 `sleep(1.2)`

**为什么原来要 sleep**：多个套件共用同一个 `edgeprof_beh` profile 目录，串行会撞锁。

**怎么解**：让 profile 可配置，各套件用独立目录：

```python
PROF = os.environ.get("UI_PROF") or os.path.join(tempfile.gettempdir(), "edgeprof_beh")
```

不设环境变量时行为与原来完全一致（单独跑不受影响）。

**效果**：13 套 × 1.2s ≈ **16 秒**。

### 优化 5：档位清理

`--fast` 只留静态四项 + CLI 自检。

原来 `--fast` 里混入了 `_test_profile`（70 秒），导致"日常档"实际要 69 秒，名不副实。
现在 `--fast` 6 秒，`_test_profile` 归到 `--full`。

## 五、试过但否决的方案

### ❌ 并行跑套件

**想法**：13 套互不依赖，并行应该快。

**实测情况**：

| 方式 | 耗时 | 结果 |
|---|---|---|
| 串行 3 套 | 13.7s | 全部通过 |
| 并行 3 套 | 4.8s | 1 套失败（DOM 长度 0） |
| 并行 4 套 | **151.5s** | 2 套超时 |

**结论**：本机 Edge **多实例并发会互相拖慢**，并行越多越慢，还会引入假失败。
**串行 + 独立 profile 才是正解。**

不要重复尝试这个方案。

### ❌ 让 `_test_profile` 改用轻量 CLI

**想法**：`--exec` 模式用不到界面，根目录的 `adb_log_export.exe`（322KB 无 UI）应该更快。

**实测**：该 exe 在自动化环境下会触发设备探测，被 sandbox 拦截超时。

**结论**：保持用 `adb_Tool.exe`，63 秒接受。反正只在 `--full` 跑。

### ❌ 减测试覆盖来提速

**不采用**。所有断言一条没删——只调整"用哪个测量通道"和"等多久"。
门禁的价值在于**能发现问题**，为了快而削弱它，是本末倒置。

## 七、给下个设备的操作建议

### 第一次跑

```bash
cd <仓库根目录>
python verify_all.py --fast      # 6 秒，先确认静态层健康
python verify_all.py             # 68 秒，功能层
```

### 如果发现某档明显变慢

按第三节的 5 个步骤查。**先量，再改**，不要凭感觉改。

### 如果本机 Edge 版本很旧

`UI_CHANNEL=wv2` 切回真实 WebView2 验证一次，确认 headless 通道在本机也一致。
（理论上升级 Edge 更好，但老旧车机环境可能有限制。）

### 新增测试套件时必须做的

1. 用**独立 profile 目录**（不要复用 `edgeprof_beh`）
2. 带上那 6 个启动优化参数
3. `timeout` 设为实际耗时的 5 倍左右
4. 跑 3 次确认没有抖动
5. 加进 `verify_all.py` 的 `EDGE_TESTS` 清单

## 八、一句话总结

> **门禁慢，90% 的时间花在"浏览器冷启动"和"等超时"上，不是花在测试逻辑上。**
> 优化方向是「减少进程启动次数」和「消除固定死等」，
> 而不是删断言、也不是并行。
