# 项目规则（约束清单）

> 每条规则都对应一次**真实踩过的坑**。没有事故背书的规则不写进来。
> 机检的部分由 `verify_all.py` 统一跑；人工判断的部分在执行前逐条对照。

---

## A. 硬规则（违反即返工）

| # | 规则 | 事故来源 | 怎么保证 |
|---|---|---|---|
| A1 | 新增 `.cs` 必须**同时**加进 `_cs/build.bat` 与 `adb_log_gui/build_gui.bat` | `Cast.cs` 第一次只加了 GUI 列表，CLI 编译仍报 "Compile success"，实际没编进去 | `_check_build_list.js`（机检） |
| A2 | `.bat` 里只写 ASCII 注释与路径 | `make_min.bat` 用中文注释，cmd 按 GBK 读，把命令行拆碎报"不是内部或外部命令" | `_check_features.js` 扫描 bat 非 ASCII |
| A3 | 新增页面 `#page-*` 必须是 `.main` 的直接子节点 | `#page-file` 插到 `#feedback` 前面，而 feedback 属于 `#page-quick`，整页空白 | `_test_structure.py`（机检 DOM 层级） |
| A4 | 任何"隐藏"而不是"覆盖"的写法都要先想清楚副作用 | 投屏最大化用 `display:none` 隐藏其它格，导致那些 `<img>` 的 multipart 流被挂起，看起来"扩大后别的投屏断了" | `_test_structure.py` + 投屏用例 |
| A5 | 诊断脚本必须走**前端真实使用的路径** | 加 `?t=` 防缓存后服务端解析崩了，而我的 `-castprobe` 没带参数，全部"通过"，把 bug 掩盖了 | `-casttest` 里加"带查询串"断言 |
| A6 | 判定要有正向证据，不能只看退出码 | `pm clear` 失败时退出码仍是 0；`screenrecord` 失败时输出 0 字节也不报错 | 相关命令都判 Success/字节数 |
| A7 | 回退必须逐字节核对 | 用 Python 读写 `ui.html` 时把 CRLF 转成 LF，`diff` 不干净 | 回退后 `diff` 目标文件 |
| A8 | 不可覆盖用户文件（同名一律加时间戳） | 用户明确要求；覆盖等于毁数据 | `FsTimeStampName` + 断言 |

## B. 流程规则（每次改动都走）

| # | 规则 | 为什么 |
|---|---|---|
| B1 | 改前先读代码，确认现状（`Grep` 找实现，不猜） | 猜错过：以为 `ls` 带权限/时间，实际只有文件名 |
| B2 | 先定协议（消息字段/输出源 src/并发归属），再写实现 | 否则出现"输出跑到别的页面""按钮点了没反应" |
| B3 | 每改一层立刻编译；不攒到最后 | `Cast.cs` 漏编能瞒过一次编译 |
| B4 | 断言优先做纯函数（`Decide` / `castMapPoint` / `FsParseLsLine`） | 只能靠真机碰运气的逻辑，抽成纯函数才能机检 |
| B5 | 交互改动必须同步改**测试断言**和**手册** | 代码改了、测试还断言旧行为，等于没有测试 |
| B6 | 交付前跑 `python verify_all.py`（全量 + 结构 + 编译列表 + 功能清单） | 单项测试全绿，也可能整页空白 |
| B7 | 交付永远两个产物：本地包 + 可分享 zip | 用户明确要求；`release.py` 固化 |

## C. 输出规则（汇报时）

| # | 规则 |
|---|---|
| C1 | 结论要带**数字**（测试通过数、体积、帧率实测值），不写"已优化" |
| C2 | 做不到的事要直说原因（如 `screenrecord` 对主屏输出 0 字节），不要用"受限于环境"糊过去 |
| C3 | 发现的坑要写进注释（`// 事故：...`），避免后人"顺手优化"回去 |

## D. 功能不丢的机制（核心）

**问题**：改动集中在同一个 `ui.html` / `GuiWeb.cs` 里，一次插入位置错、一次删除连带，就会静默弄丢一个功能，而测试只覆盖"我想到的那条路径"。

**做法**：维护一份**功能清单**（`docs/功能清单.md` + `_check_features.json`），每个功能登记：

- 用户可见行为（一句话）
- 关键落点（DOM id / 后端 case / 文件）
- 验证入口（哪个测试文件）

`_check_features.js` 会逐条检查"落点还在不在、测试文件在不在"； `_test_structure.py` 检查"四个页面结构 + 切换后容器可见"。

任何一次改动如果让某个落点消失，红灯会先亮，而不是等用户发现"功能没了"。

## E. 判据速查

| 想法 | 判据 |
|---|---|
| "应该没问题" | 有问题 —— 去加一条断言 |
| "测试都过了" | 跑的是不是**全量**？有没有结构检查？ |
| "这个改动很小" | 小改动最容易丢功能（插错一层就整页空白） |
| "工具返回 success" | 不代表产物对（`Compile success` 也可能没编进去） |
