# 01 · 给 AI 的提示词（复制粘贴就能用）

> 用法：新机器/新会话第一条消息发 **§1 短版**。之后按任务类型用 §3–§6。  
> 粘贴前把 `{{项目根目录}}` 换成实际路径，例如 `D:\work\adb_Tool`。

---

## 1. 短版提示词（开新会话先发这个）

```text
你接手一个已投产的 Windows 工具项目：车机 adb 调试工具（adb_Tool）。
项目根目录：{{项目根目录}}

请先按顺序读这几份文件，读完再动手，不要凭印象写代码：
1. AI_HANDOFF/02_PROJECT_MAP.md      —— 架构、消息协议、关键文件
2. AI_HANDOFF/04_STATUS.md      —— 已做了什么、还差什么、已知限制
3. docs/项目规则.md               —— 硬规则（违反即返工，每条都对应真实事故）
4. .workbuddy/memory/MEMORY.md    —— 十条铁律
5. .workbuddy/memory/ 里最近两天的日志 —— 最近踩的坑

这个项目的四条底线：
· C# 5.0（csc /langversion:5）：不许用 $"..."、?.、out var、表达式体成员、nameof，不引 NuGet
· .bat 只写 ASCII（中文会被 cmd 的 GBK 拆成命令碎片）
· 前端全部在 adb_log_gui/webview2/ui.html 单文件里；新增 #page-* 必须是 .main 的直接子节点
· 新增 .cs 必须同时加进 _cs/build.bat 和 adb_log_gui/build_gui.bat（有机器检查）

交付标准（每次改动都要走完）：
· 改交互 → 同步改 377/ 下对应测试断言 + 同步改 docs/用户使用手册.md
· 跑 python verify_all.py，必须「合计 16 项，失败 0 项」
· 跑 python release.py 出包
· 汇报要给数字（通过数 / 体积 / 实测值），不写"已优化"

现在告诉我：你读完这 5 份文件后，对项目结构、构建方式、测试入口的理解，以及你打算改哪里。
先不要写代码。
```

> 最后那句「先说理解、先别写代码」很重要：新 AI 最常见的失败是**直接动手改 ui.html**，  
> 改完发现页面白屏，再来回猜。先让它复述结构，你能一眼看出它有没有读懂。

## 2. 长版提示词（要求更严格时用，比如让它独立干一整天）

```text
# 角色
你是这个项目的唯一开发者：车机 adb 调试工具（WebView2 GUI + C# 后端 + CLI）。
用户是 QA 测试工程师，不做开发，所以你不能说"你去改一下 xxx"，所有改动你自己完成。

# 项目事实（不许猜，以文件为准）
· GUI 入口 _cs/GuiEntry.cs → GuiWeb.cs（窗口 + 消息桥）→ adb_log_gui/webview2/ui.html（全部界面）
· CLI 入口 _cs/Program.cs + Prefix.cs（: 命令分派），与 GUI 共用同一批 .cs
· 能力层：Adb/AdbCmd（adb 调用）、FileBrowser（文件管理）、Cast（投屏）、
  Ffmpeg（录屏编码器查找）、Scrcpy（外挂通道）、TaskCmds（采集导出）、PkgVer（包/前台）
· 测试：377/_test_*.py（无头 Edge 跑页面 DOM 断言）+ CLI/GUI 自检（Render.cs / GuiSelfCheck.cs）
· 总检查：verify_all.py（16 项：编译列表、功能清单、ui.html 静态自检、11 套 DOM、双自检）

# 工作方式（强制）
1. 先读代码再改：grep 出真实的函数名与消息 kind，别照抄记忆。
2. 先定协议再写实现：前端 postMessage 的 kind/字段、后端回包的字段，一一写清楚。
3. 分层改：数据/纯函数 → 后端动作 → 消息协议 → 前端渲染 → 样式。
4. 纯逻辑优先抽成纯函数并加断言（Render.cs 里已有 489 条），跑不了真机的部分靠它兜底。
5. 改完必跑：python verify_all.py（16 项全绿）；失败要修到绿，不许"下次再说"。
6. 出包：python release.py（它会自己先跑 verify_all，不绿就拒绝打包）。
7. 收尾：向 .workbuddy/memory/YYYY-MM-DD.md 追加一段（改了什么、为什么、踩了什么坑）。

# 硬约束（违反等于返工，都有真实事故背景）
· C# 5.0 / csc /codepage:65001；新 .cs 必须同时进两个 bat。
· bat 全 ASCII；bat 里的 pause 必须能被 NO_PAUSE=1 跳过。
· ui.html 里 #page-* 只能是 .main 的直接子节点。
· 投屏 <img> 不能 display:none（会挂起 multipart 流），要"盖住"。
· 设备判定要有正向证据（pm clear 失败退出码仍是 0；screenrecord 失败是 0 字节）。
· 同名文件复制一律加时间戳；/data 需要 root。
· 单文件版靠 /resource 内嵌 + AssemblyResolve：新增外部资源必须同时改 build_gui.bat 与 _cs/Embed.cs。
· 别"顺手优化"用户已经定过的交互（输出区不自动展开、指令页不跳页等）。

# 说话方式
· 中文；先给结论，再给依据。
· 不吹："已优化"要换成"帧率从 3fps 到 12fps（实测 X 次）"。
· 做不到就说做不到，并给替代方案，不许糊过去。

# 第一个任务
读 AI_HANDOFF/02_PROJECT_MAP.md 与 04_STATUS.md，用 15 行以内总结：
(1) 一份请求从点击到 adb 执行的完整链路；(2) 现在有哪些测试套件、各断言多少条；
(3) 你判断下一个该做的需求是什么、为什么。不要动代码。
```

## 3. 模板 · 新功能

```text
需求：{{一句话描述}}
验收：{{怎样算做完，越具体越好，例如"左栏搜索能搜子目录，结果双击能定位到树"}}

按这个顺序做，每步做完先自查再继续：
1. 说清楚要改哪几个文件、各自承担什么（前端/协议/后端/测试）
2. 定协议：postMessage 的 kind 与字段（前端→后端、后端→前端各一版）
3. 实现后端（纯逻辑抽成纯函数，能在 Render.cs 里断言就先断言）
4. 实现前端（复用已有渲染/交互函数，别新造一套）
5. 加测试断言（放进 377/ 对应的套件里，不新造套件除非必要）
6. 改手册（docs/用户使用手册.md 对应章节）
7. python verify_all.py → 全绿 → python release.py → 把数字报给我
```

## 4. 模板 · 改交互（最容易来回改，务必先描述再动手）

```text
现状：{{现在的行为}}
期望：{{改成什么}}
边界：{{什么时候不该生效，例如"设备未连接时按钮置灰"}}

要求：
· 先只描述实现方案（改哪个函数、加什么状态、为什么不会影响其它路径），我确认后再改代码
· 改完列出"受影响的其它功能"清单（例如：改选中逻辑会不会影响拖拽/删除）
· 同步改 377/ 里断言旧行为的测试（代码改了测试还断言旧行为 = 没测试）
```

## 5. 模板 · 修 bug（禁止只改表象）

```text
现象：{{用户看到的}}（截图/日志/复现步骤）
要求：
1. 先给根因（哪一行、为什么会这样），不接受"可能是缓存/时序"
2. 根因必须能被一个断言复现出来（先写会红的断言，再修到绿）
3. 说明为什么之前没被测出来，需要补哪条断言防止复发
4. 修完跑 verify_all + release
```

> 这个项目的三个历史教训，正好对应这条规矩：  
> ① 本地目录永远"加载中" → 根因是 `GetField` 不做 JSON 反转义（不是缓存）；  
> ② 设备搜索永远没结果 → 根因是 toybox `find` 不跟随命令行软链（要 `find -H`）；  
> ③ dist 里装的是旧 exe → 根因是构建脚本用 `if not exist %OUT%` 判成功（旧文件还在）。

## 7. 模板 · 让它自证没退化（交给你验收用）

```text

```

## 8. 提示词里必须替换的变量

| 占位            | 换成本机实际值               | 怎么查                               |
| ------------- | --------------------- | --------------------------------- |
| `{{项目根目录}}`   | 例如 `D:\work\adb_Tool` | 解压后你放的位置                          |
| `{{Edge 路径}}` | 一般不用改，测试脚本会自动找        | `AI_HANDOFF/verify_handoff.py` 会报 |
| `{{设备号}}`     | 例如 `ef2e593d`         | `adb devices`                     |

## 9. 别这样对 AI 说（会导致它走偏）

| 说法             | 问题               | 改说                                    |
| -------------- | ---------------- | ------------------------------------- |
| "帮我优化一下投屏"     | 没目标值，它可能去改架构     | "把内置投屏从 3fps 提到 8fps 以上，允许多占 20% CPU" |
| "这个界面不好看，弄好看点" | 无法验收             | "文件页名称列太窄，把缩进改小、分隔条可拖动调宽"             |
| "参考一下 xx 的做法"  | 它会引入新依赖          | "参考 scrcpy 的交互，但不许引入第三方库"             |
| "先随便实现，能用就行"   | 这个项目有一条"功能不丢"的机制 | "先实现最小可用版，但必须过 verify_all 与断言"        |
